Database Schema Overview

This document summarizes the database structure used by this project, based on the application source code and SQL statements found in the PHP classes.

1. Database connection

The application connects to MySQL through the class Database.

  • Localhost / local environment uses MySQL host 127.0.0.1
  • Database name is usually nbpa_data or nbpa_data_<subfolder>
  • Default credentials are defined in the code and vary by environment
$dsn = 'mysql:host=' . $this->db_host . ';dbname=' . $this->db_name . ';charset=utf8';
$db = new PDO($dsn, $this->db_user, $this->db_pass);

3. Core entity relationships

  • patient belongs to a hospital via phospital_id
  • patient is assigned to a status_id and priority_id
  • patient has multiple workflow/job records in job
  • patient can have billing records in service_billing
  • user links to hospital via uhospital_id
  • user links to user_groups via ugroup_id

Verified real tables from the SQL dump

The numbered catalog in section 2 is the complete list of 35 tables from CREATE TABLE statements in nbpa_data_dev3.sql, a MariaDB 10.4.22 dump generated on 2026-10-11.

This confirms the project includes not only patient and billing modules, but also pathology workflow, label queue logic, audit logs, user administration, and report metadata.

DDL details confirmed in the dev3 dump

  • All 35 tables use InnoDB. Character sets are mixed: most use utf8mb4, while some use utf8.
  • All tables declare a primary key except report_type, which declares a unique index on id.
  • Additional unique indexes exist on antibody_list.name, patient.pnum, and user.username.
  • The dump declares six foreign keys, all with ON DELETE CASCADE ON UPDATE CASCADE:
    • job.patient_id to patient.id
    • job.job_role_id to job_role.id
    • job.req_id to req_id_sp_slide.id
    • req_id_sp_slide.patient_id to patient.id
    • req_id_sp_slide.job_id to job.id
    • service_billing.patient_id to patient.id
  • Other columns may be indexed without being declared as foreign keys. The dump declares no foreign keys for the inferred hospital/user, patient/status, patient/specimen, result, note, or attachment links.
  • Column comments include Thai workflow descriptions on patient date/status fields, role descriptions on user.role_1 through user.role_7, and billing descriptions on service_billing.
  • specimen is not a table in this dump. service_price_list stores pricing, and patient.pspecimen_id is not constrained by a declared foreign key.

This is the schema of the dev3 dump, not proof that every deployed environment has the same schema. Re-check a fresh dump before migrations or production changes. This review used DDL only and did not use patient data rows.
