Database Backup & Hourly Sync Architecture — NB Patho (nb_web)

สถาปัตยกรรมการสำรองฐานข้อมูลรายชั่วโมง (Incremental Hourly Backup) จากเซิร์ฟเวอร์หลัก (nbpathology.com) สู่เครื่องสำรองข้อมูลผ่าน Webhook, FTP และ Desktop GUI Importer

1. คอมโพเนนต์หลักและแผนผังไฟล์ (Core Components)

คอมโพเนนต์ ไฟล์ / ที่อยู่ หน้าที่การทำงาน
Manual Web Backup UI dev3/dbtosqlfile.php หน้าเบราว์เซอร์สำหรับกดสำรองข้อมูลด้วยตนเอง เลือกย้อนหลัง 1–365 วัน ดูโครงสร้างฟิลด์ ดาวน์โหลด ZIP และลบไฟล์

2. สถาปัตยกรรมการแบ่งข้อมูล 2 ระดับ (Dual-Tier Time Partitioning)

เมื่อระบบเริ่มสร้างไฟล์สำรองข้อมูล (ค่ามาตรฐานย้อนหลัง: 10 วัน) ข้อมูลจะถูกแบ่งออกเป็น 2 ระดับอย่างชัดเจนเพื่อป้องกันไฟล์แตกกระจาย:

[ Cutoff Date: 10 วันย้อนหลัง (เช่น 2026-11-18 00:00:00) ] │ ◀── Tier 1: ข้อมูลประวัติศาสตร์เก่า (ก่อน 10 วัน) ─────┼───── Tier 2: ข้อมูลปัจจุบันรายชั่วโมง ──▶ • รวมเป็นชุดประวัติศาสตร์ชุดเดียว │ • ละเอียดเป็นไฟล์รายชั่วโมง • ข้อมูลที่ stampdatecreate < cutoffTime │ • จับทั้ง stampdatecreate & edit • แบ่งไฟล์ละไม่เกิน ~10 MB │ • แบ่งไฟล์ละไม่เกิน ~10 MB • ชื่อ: 0000-00-00_to_YYYY-MM-DD_01.sql, ... │ • ชื่อ: YYYY-MM-DD_HH0000_to_HH5959_01.sql

Tier 1: Historical Data Batch (ข้อมูลเก่าก่อน 10 วัน)

  • เป้าหมาย: ข้อมูลทั้งหมดที่ stampdatecreate < :cutoffTime (รวมถึง 0000-00-00 00:00:00 หรือ NULL)
  • การรวมกลุ่ม: รวมเป็น ก้อนประวัติศาสตร์ก้อนเดียว แทนที่จะสร้างไฟล์รายชั่วโมงหลายหมื่นไฟล์ในอดีต
  • ข้อได้เปรียบของการเรียงชื่อ (A-Z): เนื่องจากชื่อไฟล์ขึ้นต้นด้วย 0000-00-00_to_... การเรียงลำดับไฟล์ตามตัวอักษรจะทำให้ข้อมูลเก่าถูก Import เข้าฐานข้อมูลก่อนไฟล์รายชั่วโมงของปัจจุบันเสมอ

Tier 2: Recent Incremental Hourly Data (ข้อมูล 10 วันล่าสุด)

  • เป้าหมาย: ข้อมูลที่สร้างใหม่ (stampdatecreate) หรือมีการแก้ไข (stampdateedit) ภายใน 10 วันล่าสุด
  • การรวมกลุ่ม: แยกไฟล์เป็นรายชั่วโมง (เช่น 2026-11-28_110000_to_115959_01.sql)

3. ไวยากรณ์ SQL Upsert (ON DUPLICATE KEY UPDATE)

ไฟล์ SQL สำรองทุกไฟล์ใช้ไวยากรณ์ Upsert ของ MySQL เพื่อความปลอดภัย 100%: 

INSERT INTO `table_name` (`id`, `col1`, `col2`, ...)
VALUES (101, 'val1', 'val2', ...)
ON DUPLICATE KEY UPDATE `col1`=VALUES(`col1`), `col2`=VALUES(`col2`), ...;
Idempotent Safety: 1. ถ้าเป็นเรคคอร์ดใหม่: ทำงานเป็น INSERT ปกติ
2. ถ้ามี Primary Key อยู่แล้ว: ทำงานเป็น UPDATE ข้อมูลล่าสุดทับลงไป
3. สามารถนำเข้าซ้ำกี่ครั้งก็ได้โดยไม่มีวันเกิด Error #1062 - Duplicate entry

4. ลำดับการนำเข้าข้อมูล (Import Execution Order)

โปรแกรม db_backup_sync_gui.py บนเครื่องปลายทางจะนำเข้าข้อมูลตามลำดับต่อไปนี้อย่างเคร่งครัด:

  1. ขั้นตอนที่ 1: รันไฟล์ a_initial_table.sql เพื่อสร้างโครงสร้างตาราง (CREATE TABLE IF NOT EXISTS) ทั้ง 36 ตารางให้พร้อมก่อน
  2. ขั้นตอนที่ 2: รันไฟล์ประวัติศาสตร์ 0000-00-00_to_YYYY-MM-DD_*.sql ตามลำดับพาร์ท (01, 02, ...)
  3. ขั้นตอนที่ 3: รันไฟล์รายชั่วโมง YYYY-MM-DD_HH0000_to_...sql จากชั่วโมงเก่าสุดไปหาใหม่สุด
